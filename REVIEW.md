# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | Global / app startup (missing lifespan) | No database indexes were created at startup. | Inspecting MongoDB indexes shows only `_id`. Queries do `COLLSCAN` and concurrent duplicate inserts succeed or cause data corruption. | Added FastAPI lifespan context manager that idempotently creates indexes on `employees` (`emp_code`, `department+joined_on`) and `attendance_logs` (`emp_code+date`, `date+emp_code`, `date+late_minutes`, `emp_code+punch_in`). |
| 2 | `health` (lines 72-74) | Always returned `{"status": "ok"}` without checking if MongoDB is reachable. | Stopping MongoDB container still yields HTTP 200 instead of required 503 readiness probe response. | Added `client.admin.command("ping")` probe; catches exception and raises HTTP 503. |
| 3 | `compute_late_minutes` (lines 33-38) | Truncated `(punch_in - start).total_seconds() / 60` to `int` before checking `minutes > 10`. Also failed to handle overnight shifts and timezones. | Shift 09:30, punch in at 09:40:01 IST: elapsed is 10.016 min, `int` is 10, `10 > 10` is False, returning 0 late minutes instead of 10 (violating R2). | Checked `(punch_in - start_dt).total_seconds() > 600` strictly, computed floor minutes from `shift_start`, and properly resolved shift start on the attendance date. |
| 4 | `compute_work_hours` (lines 40-41) | Used Python's built-in `round()`, which applies banker's rounding (round to even). | Work duration of 2.675 hours produces `2.67` instead of `2.68` (violating R4 half-up rule). | Implemented `round_half_up` helper using Python `Decimal` with `ROUND_HALF_UP`. |
| 5 | `compute_overtime` (lines 44-48) | Returned `max(0, minutes)` without enforcing the 30-minute threshold. Also assumed shift end falls on punch-in date. | 15 minutes past shift end returned 15 overtime minutes instead of 0 (violating R3). Overnight shifts compared against the wrong date. | Enforced `diff_sec >= 1800` (30 minutes) threshold; resolved overnight shift end to next calendar day. |
| 6 | `create_employee` (lines 77-85) | Check-then-insert race condition. Lacked schema validation (regex pattern, email validation, shift time check). Returned ISO datetime string. | Concurrent creation of same `emp_code` created duplicates or unhandled 500s. Returned `created_at` as ISO string instead of epoch milliseconds. | Enforced database unique index on `emp_code`, caught `DuplicateKeyError` returning 409, added Pydantic validations, and serialized `created_at` as epoch milliseconds integer. |
| 7 | `list_employees` (lines 88-96) | Off-by-one pagination bug: `skip = page * page_size`. Total counted entire collection ignoring filters. Unsorted. | Requesting `page=1` skipped the first 20 records. Total ignored department filter. Items returned in arbitrary order. | Changed skip to `(page - 1) * page_size`, passed filter `q` to `count_documents`, and sorted by `emp_code` ascending. |
| 8 | `punch_in` (lines 99-122) | Missing employee check threw unhandled 500 on `emp["shift_start"]`. Check-then-insert race condition. Injected invalid `"id"` into response. Ignored overnight shifts. | Unknown `emp_code` crashed with 500 instead of 404. Duplicate requests crashed with 500. Output contained `"id"` forbidden by contract. Overnight shifts assigned wrong date. | Added employee 404 check, caught `DuplicateKeyError` as 409, removed `id` field, and assigned attendance date via R1 overnight shift logic. |
| 9 | `list_attendance` (lines 124-151) | Loaded the entire collection into memory with `list(db.attendance_logs.find(q))` and sorted in Python. No date validation. | High memory consumption and severe latency on ~100k records. `date_from > date_to` did not return 422. | Replaced in-memory sorting with MongoDB query `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)` backed by compound index; added date range validation (422). |
| 10 | DateTime handling & whole-second truncation | Instants were not truncated to whole seconds (R1), and serialization leaked datetime objects or naive timestamps. | Sub-second timestamps caused arithmetic drift in late/overtime calculations and response serialization errors. | Implemented `truncate_millis` helper to truncate to whole seconds before calculation and storage; converted cleanly to UTC BSON in database and epoch milliseconds in API. |

### Examined and Deemed Not a Defect
- **Synchronous PyMongo Client**: Evaluated whether PyMongo should be replaced with Motor (async). PyMongo is fully supported by the specification ("PyMongo or Motor") and FastAPI dispatches synchronous endpoints to an optimized worker thread pool. With proper compound indexes and MongoDB aggregations taking single-digit milliseconds, PyMongo provides simpler concurrency semantics and robust transaction/update handling without async driver overhead.
